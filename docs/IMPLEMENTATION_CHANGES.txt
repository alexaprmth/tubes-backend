2. RETURN, UANG DAN LIFECYCLE RENTAL
- Frontend return mengirim JSON.stringify, sehingga server tidak menerima
  body [object Object] atau JSON yang tidak bisa diparse.
- Tanggal rental harus format YYYY-MM-DD dan hari kalender yang benar.
  EndDate harus sesudah StartDate. Return tidak boleh sebelum rental dimulai.
- Denda kerusakan harus number, finite, rupiah bulat, tidak negatif.
  String, NaN, Infinity, pecahan dan nominal melebihi batas ditolak.
- Satu hari terlambat dihitung satu hari, dengan tarif 25% harga harian yang
  dibulatkan; perhitungan demo disamakan dengan tanggal UTC yang dipakai SQL.
- Perhitungan/validasi dilakukan sebelum inspeksi/fine/status ditulis.
- Refund dihitung max(0, deposit - fine), memerlukan return pending dan
  refund pending. Sengketa terbuka menahan konfirmasi refund.
- Rental COMPLETED menutup reservasi menjadi COMPLETED. Kendaraan rusak,
  GPS tidak siap atau maintenance tidak langsung dinyatakan AVAILABLE.
- Pembayaran dan refund yang diulang tidak membuat record baru atau
  mengubah kendaraan yang sudah dipakai oleh rental berikutnya.
- Sengketa memakai transaksi/guard lifecycle; fitur penyelesaian sengketa
  produksi yang lengkap tidak ditambahkan dalam scope ini.

3. ATOMIC WRITE DAN STATUS KENDARAAN
- Penulisan Supabase reservation/payment/handover/return/refund/maintenance
  dan sengketa memakai transrent_transaction, bukan update tabel terpisah.
- Fungsi SQL membaca profile aktor untuk role/company/verification dan
  mengunci kendaraan terlebih dahulu, lalu record transaksi terkait.
- Rental, reservation, vehicle, inspection/items/photos, fine dan refund
  yang terkait disimpan dalam transaksi yang sama. Error membatalkan write.
- Partial unique index mencegah dua rental aktif pada kendaraan yang sama,
  dan lebih dari satu pembayaran PAID untuk reservasi yang sama.
- Handover ditolak jika kendaraan telah disewa/return inspection/maintenance.
  Maintenance tidak menimpa kendaraan yang masih memiliki rental aktif;
  kendaraan INACTIVE tidak diaktifkan lewat maintenance.
- Penyelesaian maintenance mengecek rental/maintenance lain dan GPS sebelum
  mengembalikan AVAILABLE. Retry refund tidak melepaskan kendaraan baru.
- File Storage bukan satu transaksi dengan PostgreSQL. Inspeksi memakai
  path UUID immutable; file attempt gagal dibersihkan sebisa mungkin.
  Foto/signature inspeksi harus data URL PNG/JPEG/WebP, bukan path arbitrer.

2. PENYELESAIAN SENGKETA
- Customer melihat denda dan mengajukan sengketa melalui menu Rental & denda.
- Admin Rental hanya memutuskan perusahaan sendiri; Admin Pusat lintas perusahaan.
  Customer/staff tidak dapat mengesahkan keputusan admin.
- ACCEPTED: seluruh denda terkait dihapus (amount=0, fine CANCELLED).
- REJECTED: nominal denda dipertahankan, fine APPROVED.
- ADJUSTED: nominal akhir rupiah bulat 0..nominal awal, fine APPROVED.
- Alasan keputusan wajib. Disimpan original_amount, final_amount, resolved_by,
  resolution_notes dan resolved_at pada fine_disputes. Keputusan final tidak

  Sengketa OPEN/DISPUTED memblokir pelunasan dan penutupan rental.
- Menghapus kewajiban membayar kerusakan tidak menghapus kondisi rusak fisik.

3. PELUNASAN SELISIH DENDA
- Formula: fineTotal = SUM(denda non-CANCELLED).
  depositApplied = MIN(deposit, fineTotal).
  balanceDue = MAX(0, fineTotal - deposit - finePayment.amount).
  refundAmount = MAX(0, deposit - fineTotal).
- Contoh sintetis: deposit Rp500.000, denda Rp800.000 -> selisih Rp300.000.
  Bila keputusan admin mengubah denda menjadi Rp700.000 -> selisih Rp200.000.
- Hanya customer pemilik rental membayar melalui simulator. Nominal selalu
  dihitung server, tidak memakai nominal yang dikirim browser.
- Satu pembayaran penuh per rental disimpan di fine_payment JSONB dengan ID,
  provider/reference, amount, paidBy, paidAt dan PAID. Retry bukti yang sama.
- Pembayaran menjadikan denda final APPROVED; pengajuan sengketa ulang diblokir.
  UI meminta persetujuan nominal sebelum customer menjalankan pembayaran.
- Admin tidak dapat menutup rental/refund selama masih ada balanceDue > 0.
  Status tetap RETURN_PENDING_REVIEW sampai sengketa/selisih selesai.
- Rental lama yang sudah COMPLETED tetapi memiliki selisih juga dapat dilunasi.
  Bundle melaporkan jumlahnya untuk rekonsiliasi: jangan menagih ulang jika
  ternyata pernah dibayar di luar aplikasi. Migrasi tidak mengarang bukti bayar.

4. KENDARAAN RUSAK TIDAK MENJADI AVAILABLE KARENA CANCEL MAINTENANCE
- vehicles.repair_required adalah penanda kondisi fisik yang persisten.
  Return dengan damageItems menandainya true, terlepas dari nominal/putusan denda.
- Kendaraan rusak tetap MAINTENANCE setelah penutupan rental. Pembayaran denda
  bukan bukti perbaikan. Cancel SERVICE/REPAIR tidak membersihkan flag kerusakan.
- Hanya penyelesaian REPAIR, dengan tidak ada REPAIR lain aktif, membersihkan
  flag. Status AVAILABLE juga mensyaratkan GPS READY, tidak ada maintenance
  aktif lain, tidak ada rental aktif, serta status kendaraan dapat dipulihkan.
- Menyelesaikan SERVICE biasa tidak membersihkan kerusakan. Jika satu REPAIR
  selesai saat REPAIR lain belum selesai lalu yang tersisa dibatalkan, flag
  tetap true: perlu REPAIR selesai yang benar-benar menutup pekerjaan kerusakan.
- Backfill konservatif untuk data lama: cari kerusakan rental tanpa REPAIR
  COMPLETED yang waktunya sesudah kerusakan. Flag true; kendaraan AVAILABLE/
  RESERVED dipindah ke MAINTENANCE. Tidak mengubah rental aktif/INACTIVE.
